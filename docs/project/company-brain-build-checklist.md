# Company Brain. Чеклист сборки и промышленного выпуска

Первый процесс: передача задачи на разработку кода, независимая проверка патча и приёмка конкретного коммита. Владелец процесса: заказчик Company Brain. Первый экземпляр: закрытый стенд на этом Mac. Принимающий: отдельный оператор, которого назначает владелец.

Один запуск означает один журнал и один граф работ от вводных до релизного пакета. Очередь сохраняет состояние при перезапуске. Автор и верификатор работают через подписки Codex GPT-6.2 Sol xhigh и AGY Gemini 4 Hydrogen xhigh. В подписочный контур попадают только публичные или синтетические материалы. Оператор принимает SHA каждого среза, выполняет слияние и принимает выпуск. Владелец заранее делегирует эти решения в пределах согласованного периметра.

Первый сквозной кейс проходит путь **бриф → правило с версией и источником → пакет передачи → патч → проверки → замечание или приёмка → история и откат**. Исходный контрольный случай для стенда: обычные тесты зелёные, но патч падает на допустимом предельном входе. Для реального пилота оператор фиксирует один обезличенный возврат и ожидаемое поведение до реализации.

## Как отмечать выполнение

У каждого пункта записываются статус, ответственный и ссылка на свидетельство. Для машинных проверок сохраняются SHA версии, команда, время и выходной код. Рабочие статусы: **открыт**, **подтверждён**, **отклонён**, **вне области пилота** с причиной. Отложенный пункт сохраняет владельца и условие возврата. Промышленный выпуск требует подтверждения всех применимых критических пунктов в целевом окружении.

Технические решения для первого выпуска: стартовое Git-хранилище с Markdown, переход к одному серверному экземпляру с SQLite, FTS и неизменяемыми ревизиями, браузерный интерфейс для приёмки и тонкий MCP/CLI интерфейс для агентов. Хранилище и SDK принадлежат Company Brain. Запуск исполняемого кода в серверной песочнице принимается в целевой среде. Векторный поиск, кластер, отдельный репозиторий Control Center, сбор истории внешних чатов и новые интеграции добавляются по подтверждённой потребности и разрешённому охвату.

## Пороги и границы первого прогона

- Техническое условие выпуска. 8 из 8 адаптированных BDD, 100% применимых критических проверок, ноль подтверждённых нарушений границ, успешные восстановление и откат.
- Предлагаемые параметры первого закрытого пилота. Не больше двух авторов, один верификатор, максимум две работы одновременно в работе или ревью. По умолчанию работа начинается с меньшего параллелизма, пока зависимости и проверка не выдержат две задачи.
- Стартовые ориентиры восстановления стенда. RPO до 24 часов и RTO до 60 минут. Оператор подтверждает или корректирует их до замера. Для корпоративной среды применяются согласованные параметры площадки.
- Экономика. $(стоимость всех попыток + ручное ревью + исправления) / число принятых задач$. При нуле принятых задач показатель неопределён. Сохранить размер выборки, долю приёмки и календарное время. Если модельные затраты оцениваются через официальный тариф API, отдельно учитывать кешированные входные токены с их тарифом, отмечать источник ставок и отсутствующую телеметрию. Такая оценка отражает эквивалентное потребление, а не расход по подписке.
- Свидетельство закрытого стенда на Mac подтверждает именно этот контур. Для выпуска в корпоративную среду нужны её параметры, разрешённые источники и испытания на месте.

## Как пройдёт один запуск Swarm

1. Оператор открывает отдельный репозиторий и отдельный runtime в области активного launcher. Привязывает ID прогона, профиль, лимиты, граф и evidence-каталог. Защищённые тесты и исходные правила закрепляются до передачи автору.
2. Координатор готовит только готовые по зависимостям задачи. В текущем Swarm базовый SHA фиксируется в **submit**, поэтому нельзя заранее отправить весь граф. После каждого слияния координатор читает новый HEAD и только тогда ставит следующую зависимую задачу.
3. Для каждой задачи Swarm выдаёт отдельный worktree, запускает автора и передаёт кандидат независимому верификатору. Срез ограничен 7 файлами и 350 изменёнными строками. Большой пункт разбивается на несколько последовательных срезов с той же целью и отдельными доказательствами.
4. Оператор сверяет результат с контрактом и конкретным SHA из ReviewPacket. Затем принимает SHA и сливает с ожидаемым HEAD. Зависимость открывается только после статуса `done`. Если HEAD изменился, оператор повторно проверяет кандидат перед слиянием.
5. При временном сбое координатор сохраняет журнал и продолжает через штатные команды запуска и адресного возобновления. При исчерпании квоты, неоднозначном источнике или отсутствии полномочий останавливается только затронутая ветка. Непройденный критический контроль блокирует выпуск.
6. В конце оператор выгружает список принятых SHA, результаты закрытых и сквозных проверок, пакет релиза, отчёт пилота и протокол восстановления. Закрытый стенд и корпоративный выпуск имеют отдельные решения о готовности.
