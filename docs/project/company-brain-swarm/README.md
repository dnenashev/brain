# Пакет запуска Company Brain в Swarm

Пакет сопровождает [чеклист](../company-brain-build-checklist.md). Он включает граф, восемь BDD-примеров и регрессию на синтетических данных, генератор TaskSpec и защищённый раннер. Назначенный оператор ведёт один журнал сборки и принимает SHA. Владелец процесса подключается только при изменении согласованного периметра.

## До старта

1. Закрепить имя принимающего, полномочия на принятие коммитов и закрытый выкат. Указать замену или способ эскалации. Заполнить карточку первого процесса одним обезличенным брифом и прошлым возвратом, либо записать, что первый прогон использует учебный кейс. Для подтверждения реальной ценности всё равно нужны реальные работы и их исходные метрики.
2. Использовать собственный изолированный репозиторий, отдельный runtime и каталог артефактов внутри области launcher. Скопировать в Git только публичные или синтетические входы. Перед каждым заданием независимо подготовить `checks/test_<id>.py`, зафиксировать хеш и проверить провал на плохом варианте. Первый пример есть в `bootstrap/test_cb11.py`.
3. Оператор ведёт доверенный журнал. Запись ручного контроля имеет вид `{"evidence":"архив/протокол.json"}`. У выполненной задачи добавляется `"merged_sha"` с SHA из Swarm после слияния. Фиксировать результат только после проверки свидетельства. Каталог журнала находится вне checkout и полномочий автора.
4. Перед постановкой проверить активный релиз, конкретный профиль, состояние очереди, доступ к подпискам и лимиты. Настоящие учётные данные не копировать. Для закрытого holdout использовать отдельную директорию вне checkout автора и операторскую проверку выбранного SHA. Свидетельства пилота и данные с ограничениями хранятся отдельно от синтетического проекта.

## Рабочий цикл

Из корня Swarm, сохраняя один и тот же ID прогона и каталог состояния:

```sh
pack='/path/to/brain/docs/project/company-brain-swarm'
run='.swarm/company-brain-build'
python3 "$pack/prepare.py" validate
python3 "$pack/prepare.py" ready --journal "$run/control/journal.json"
```

Для каждого готового задания, после подготовки защищённого теста:

```sh
task=CB11
python3 "$pack/prepare.py" spec "$task" --repo "$run/repo" \
  --journal "$run/control/journal.json" > "$run/control/next-task.tmp" &&
  mv "$run/control/next-task.tmp" "$run/control/$task.json" &&
  .swarm/production/swarm --repo "$run/repo" --run-dir "$run/runtime" \
  --budget-config "$run/control/budget.json" submit "$run/control/$task.json"

.swarm/production/swarm --repo "$run/repo" --run-dir "$run/runtime" \
  --budget-config "$run/control/budget.json" run-ready --authors 1 --verifiers 1 --wip-limit 2

.swarm/production/swarm --repo "$run/repo" --run-dir "$run/runtime" review "$task"
```

Оператор сверяет разницу, отчёт и SHA кандидата. Перед фиксацией следующего подтверждения запускает дополнительные сквозные проверки, указанные в критериях задачи. Для независимых ветвей допускаются два автора и один верификатор после подтверждения, что срезы не пересекаются. Если сборка не завершилась, оператор сверяет `status` и `health`. Возобновление использует существующий runtime. Повторная постановка уже существующего ID пропускается после сверки с очередью. При подтверждённой просрочке квоты применяется порядок `stop` и `wake` из runbook Swarm.

Только после решения принимающего:

```sh
.swarm/production/swarm --repo "$run/repo" --run-dir "$run/runtime" approve "$task" "$candidate"
.swarm/production/swarm --repo "$run/repo" --run-dir "$run/runtime" merge "$task" "$expected_head"
```

`candidate` берётся из принятого ReviewPacket, `expected_head` сверяется с текущим Git HEAD. Записать интегрированный SHA и доказательства в журнал и повторить `ready`. Генератор читает текущий чистый HEAD, проверяет наличие закреплённого раннера и теста, требует свидетельства предшественников и убеждается, что их слитые SHA входят в историю. Он выводит контракт. Приёмку и слияние выполняет оператор.

Если срез превышает ограничение Swarm, оператор выделяет меньшие срезы с отдельными тестами, включает их в граф с соответствующими пунктами журнала и повторно прогоняет `validate`. Подробности остановки, независимой проверки и допуска к выпуску закреплены в основном чеклисте.

## Первый сквозной кейс

`pilot-cases.json` содержит исходные состояния, действия и ожидаемые результаты, включая один допустимый предельный вход. Оператор держит закрытую вариацию отдельно. Значения из учебного примера не используются как политика реального проекта.

Первый проверяемый артефакт среза CB11 имеет файлы `docs/core.md` и `docs/processes/development.md`. Для ядра обязательны разделы `Цель`, `Словарь`, `Инварианты`, `Роли`. Для процесса обязательны `Вход`, `Передача`, `Проверка`, `Приёмка`, `Возврат`. Тест проверяет наличие разделов и текста, а принимающий проверяет непротиворечивость полномочий и словаря.
