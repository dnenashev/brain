# ADR 0001. Спецификации процесса разработки в пилоте Company Brain

## Решение

Фиксируем действующее учебное правило версии `plan-v2` и таймаут по умолчанию `5000` мс в описании текущего поведения. Новое требование обрабатывает `300000` мс как допустимую верхнюю границу запрошенного таймаута. Для проверки публикуем восемь BDD-сценариев и регрессию `REG01` с исходными данными, ссылками на правила и наблюдаемыми результатами. [Текущее поведение](../current/development.md) · [Новое требование](../../specs/behavior/timeout-change.md) · [Сценарии пилота](../../specs/behavior/pilot.v1.json)

## Причины

У значения по умолчанию и допустимой верхней границы разные назначения. Раздельные документы позволяют сверить действующее значение с утверждённой версией правила, а предлагаемую границу проверить по `REG01`. Примеры `0`, `299999`, `300000` и `300001` показывают, какие значения принимаются и какие отклоняются. [Правило REG01](../../specs/behavior/timeout-change.md#timeout-boundary)

## Свидетельства и приёмка

Ожидаемые значения берём из публичного синтетического набора, предоставленного оператором в задаче `CB13-R2`. Независимый верификатор сверяет допустимые пути, соответствие сценариев задаче и достаточность свидетельств по diff кандидата. После положительного заключения Swarm запускает защищённую проверку. Оператор фиксирует подтверждённые результаты и решение о приёмке для точного SHA кандидата. [Процесс разработки](../processes/development.md)
